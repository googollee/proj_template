# Review 指南

review 的核心：对照每类文档的目标和范围，检查是否有越界内容。越界内容移到正确的文档，或直接删除。

## prd

**目标**：说明项目要解决什么问题、为谁解决、在什么场景下用，以及不做什么。

**应包含**
- 背景与目标
- 用户
- 场景
- 需求（`F-001` 编号，每条可验收）
- 非目标

**不应包含**
- 技术方案、技术选型
- 模块划分、数据结构、接口
- 实现步骤、排期
- 决策过程与备选方案

**典型越界示例**

- 「使用 Redis 缓存查询结果」 → 写成性能需求；选型放 ADR
- 「系统分为 API 层和存储层」 → design
- 「先做登录，下周做导出」 → 不属于文档，放任务工具

**检查项**
- 每条需求有稳定编号，标题只写编号，名称在下一行
- 每条需求能被验证
- 非目标已列出

## adr

**目标**：记录一个决策：当前选了什么，依据是什么，考虑过哪些备选。

**应包含**
- 决策（只描述当前决策）
- 依据（链接 PRD 需求）
- 备选方案（每项标「未采纳」）
- 影响

**不应包含**
- 需求本身的描述
- 决策的演进史
- 实现步骤、代码细节
- 多个互不相关的决策

**典型越界示例**

- 「用户需要离线使用，因为……」 → prd，ADR 只链接 `F-003`
- 「最初用 A，后来改成 B」 → 删除；新决策取代旧决策时，旧 ADR 标放弃
- 「第一步建表，第二步写迁移」 → 不属于文档
- 同一份 ADR 同时决定存储和鉴权 → 拆成两份 ADR

**检查项**
- `status` 以「提案中 / 发布 / 放弃」之一开头，放弃有括号原因
- 有「备选方案」一节，且每项标「未采纳」
- 需求以链接引用，没有复述
- 英文 slug 文件名，四位编号不重复

## design

**目标**：描述项目当前的中高层设计：怎样划分、各部分如何协作。

**应包含**
- 概述
- 组成与职责
- 协作方式
- 关键接口（可含签名）
- 相关决策（链接 ADR）

**不应包含**
- 需求的复述
- 决策依据与备选方案的展开
- 函数体、字段级的实现细节
- 变更历史

**典型越界示例**

- 「用户希望能离线使用，所以……」 → prd，设计只链接
- 「选 SQLite 是因为比 Postgres 轻量」 → adr，设计写结论并链接
- 「v2 把同步模块拆出来了」 → 删除，历史靠 git
- 逐个列出内部私有函数 → 代码

**检查项**
- 引用的 ADR 都是「发布」状态
- 能解释各部分为何这样划分
- 代码与设计一致
